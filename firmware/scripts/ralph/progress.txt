## Codebase Patterns
- Entity globals are in `ui/data.h` + `ui/data.c` (Badge, Machine, Tank, g_badges, g_machines, g_tanks, g_badge_count, etc.)
- The build environment requires IDF_PATH setup; source /Users/I584748/esp/esp-idf/export.sh before idf.py
- Pre-existing CMake issue: `gdbinit.cmake:40` fails with "exactly three arguments" error; does not affect compilation
- Build: `idf.py build` fails with cmake 4.3.2; use direct riscv gcc compile from compile_commands.json to verify individual files
- LVGL is pinned to CPU1 (task_affinity=1 in bsp_display_cfg_t); all other tasks (sim, mqtt, btn, console) should use CPU0 or auto
- LVGL draw buffers MUST stay in internal DMA-capable SRAM (buff_spiram=false, buff_dma=true); buff_spiram=true causes UI freeze
- Screenshot tool: python3 tools/screenshot.py from firmware/ dir
- wifi_manager.c handles NVS, scan, connect, AP mode; already uses lv_async_call for conn_dispatch and scan_dispatch — follow same pattern for any new UI notifications
- mqtt_task.c: disable_auto_reconnect=true; exponential backoff via esp_timer_one_shot (5s→10s→30s)
- THREAD SAFETY RULE: Any code running outside the LVGL task (sim_task, mqtt event handler, wifi event handler) must NEVER call LVGL APIs directly. Use lv_async_call() trampolines. Trampoline pattern: malloc a small struct, set fields, call lv_async_call(cb, struct); in cb call the UI function then free(struct). Always check lv_async_call() return value and free on LV_RESULT_INVALID.
- DATA MUTEX: g_machines and g_tanks are shared between sim_task (CPU0, writes) and LVGL refresh timers (CPU1, reads). Protect all reads/writes with DATA_LOCK()/DATA_UNLOCK() macros (defined in ui/data.h, backed by g_data_mutex FreeRTOS mutex created in data_init_psram()).
- LVGL TASK STACK: Default 7168 bytes is insufficient for complex UIs. With 7 machines × multi-widget cards, ui_machines_create() overflows the stack. Set cfg.lvgl_port_cfg.task_stack = 20480 in bsp_display_cfg_t init.
- Flash to device: idf.py flash (port auto-detected as /dev/cu.usbmodem5B610403841)
- Serial monitor requires TTY; use python3 -c with pyserial for headless capture instead of idf.py monitor

## 2026-05-11 - US-003 (part 2 — LVGL task stack overflow)
- Increased LVGL task stack from 7168 (default) to 20480 bytes in main.c bsp_display_cfg_t
- Root cause: Stack protection fault on Core 1 at boot (~5.6s), before any navigation
- Serial log showed SP=0x4ff39360 below stack bottom 0x4ff39370; crash was deterministic at boot not on navigation tap
- 7 machines × complex cards (sparkline chart + arc gauges + metric tiles) in ui_machines_create() exhausted 7KB during initial UI build
- Files changed: main/main.c
- **Learnings:**
  - Stack overflow manifests as cyan screen (same symptom as LVGL assert) — serial log is essential to distinguish causes
  - Crash at boot before user interaction = stack/init problem, not a race condition
  - idf.py monitor requires TTY; use python3 pyserial script for headless serial capture
  - With complex LVGL UIs (many nested objects), 7KB LVGL task stack is insufficient; 20KB is safe headroom for this config
